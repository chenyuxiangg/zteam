# v2 工程分层模型设计（P1-01 / P1-02 / P1-04 完整方案）

> 状态：**实施中**（第 1-4a 期已完成并验证；4b/5/6 待实施，见每节标注）
> 目标模型（用户拍板）：**项目 → M 版本 → N 需求（依赖关系）→ X 迭代（迭代内并行、迭代间串行）→ UT（需求级）/ IT（迭代级）/ ST（版本级）**
> 设计原则：在现有四态状态机/项目锁/阶段链上**增量演进**，存量 released 数据零破坏。

## 0. 设计全过程（怎么想的）

1. **目标模型**：按用户 P1-04 期望（项目→版本→需求→迭代→三层测试），对照现状（一需求跑全链、无版本/迭代/分层测试），差距 = 版本维度缺失 + 依赖缺失 + 迭代缺失 + 测试只有 UT。
2. **约束**（用户拍板 4 点）：①版本语义化；②自动排期 + 人工干预途径；③变更三分场景；④自动跑。
3. **增量路线**：不推翻现状——现有"需求四态状态机 + 项目锁 + 阶段链"全部保留，**逐期叠加**（版本 → 依赖 → 迭代 → 测试分层 → 变更），每期独立验证提交，存量数据只补元数据。
4. **关键设计决策**（见各节）。

## 1. 数据模型（已实施）

### 1.1 需求 entry（status.json，已实施）

```
status:      pending/analyzing/analyzed/reviewing/approved/
             {stage}_designing/{stage}_reviewing/{stage}_done/
             waiting(新)/blocked/released/needs_fix...
version:     "v1.0.0"          # 归属版本（投放文件头指定，默认项目 current）
iteration:   1                  # 归属迭代（自动排：无依赖→1；有依赖→max(依赖迭代)+1；assign 可覆盖）
depends_on:  ["req-b", ...]     # 依赖需求（approved/released 解锁）
stages:      {阶段: {state: claimed/working/reviewing/done, product, reviews, ...}}
```

### 1.2 versions.json（项目级，已实施）

```json
{
  "versions": [{
    "name": "v1.0.0",
    "status": "released",       // planning → in_dev → st_pending → st_passed → quality_pending → released
    "iterations": [             // 迭代对象（旧格式 [1,2] 自动迁移）
      {"n": 1, "status": "it_passed", "reqs": ["req-a"], "it_product": "demo/it/iter-1/", "it_reviews": [...]}
    ],
    "reqs": ["req-a"],          // 版本归属需求
    "st_product": null,         // ST 产物（4a 已写，4b 接门禁/发布）
    "released_at": "..."
  }],
  "current": "v1.1.0"           // 当前开发版本（新需求默认归属）
}
```

## 2. 状态机（已实施）

| 层级 | 状态链 |
|---|---|
| **需求级**（四态 + 新增） | pending → analyzing → analyzed → reviewing → approved → plan_designing→…→ **test_done（v2 截断点）**；新增 **waiting**（依赖/迭代前置未满足，零 token 挂起）；blocked（failures≥2/max_rounds，人工 requeue） |
| **迭代级**（新） | pending → it_pending（it-designer 执行中）→ it_passed（release_it PASS）/ 打回 it_pending 重做 |
| **版本级**（新） | planning → in_dev → st_pending（全迭代 IT PASS）→ st_passed（release_st PASS）/ 打回 → quality_pending（4b）→ released（4b） |

## 3. 调度过程（tick 每 5 分钟 × 每项目锁内，已实施）

```
tick（每项目锁内，顺序执行）：
1. register       新需求注册：文件头解析 version:/iteration:/depends_on:，默认 current 版本，
                  versions.json 维护 reqs/iterations 归属（幂等）
2. _apply_deps    依赖 + 迭代检查：pending 且前置未满足 → waiting；
                  waiting 且满足 → pending；自动排迭代（无依赖→1，有依赖→max+1）
3. stale/guard    巡检：卡死 worker 补正、漏设状态兜底
4. _advance_v2    迭代状态机：迭代全需求 UT done + it_passed → 累计 → 版本 st_pending
5. _schedule_it_st 测试分层调度：
                  - 迭代内全部需求 test_done/released → spawn it-designer（产物 {项目}/it/iter-{N}/）
                  - 版本 st_pending → spawn st-tester（产物 {项目}/st/{版本}/）
6. find_claimable 认领一个需求 → spawn 对应角色 worker（一次一个，防唤醒风暴）
```

**等待零 token**：waiting 态需求不认领不 spawn（依赖未满足/前序迭代未完成时），满足后自动转 pending。

## 4. 测试分层流转（4a 已实施，4b 收口）

```
每需求：req → plan → testplan → code → test（=UT，通过 → test_done 截断，不再进需求级发布）
每迭代：迭代内全部需求 test_done → it-designer 集成测试（接口/协作用例）
        → release_it PASS → 迭代 it_passed（FAIL → 重做，it_claimed 重置）
每版本：全部迭代 it_passed → st-tester 系统测试（端到端主链路/回归）
        → release_st PASS → 版本 st_passed（FAIL → 重做）
        → [4b] 质量/安全门禁（版本级）→ releaser 版本级发布 → 版本 released
```

角色（新增 4 个）：it-designer（flash）/ it-reviewer（pro）/ st-tester（flash）/ st-reviewer（pro）——角色文件已建（评审检查清单/产出模板/结论区规范）。

## 5. 变更三分场景（P1-02，第 5 期设计）

| 场景 | 处理 | 状态机 |
|---|---|---|
| **修改需求** | `change_request <req_id> "<描述>"` → 需求回 analyzing，**全链重跑该需求**（保留已通过阶段评审历史作参考） | 复用 requeue 续跑机制 + 修订轮 |
| **删除需求** | `change_request --remove <req_id>` → 从版本/迭代/versions.json 移除，**忽略该需求**；依赖它的需求解除阻塞（_deps_satisfied 已处理依赖不存在不阻塞） | waiting → pending 自动解锁 |
| **新增需求** | 正常投放（zbot/input），自动排迭代 | 第 1-3 期已就绪 |
| 版本冻结 | 已 released 版本不可修改，变更需开新版本（v1.1.0）承载 | 4b/5 实施 |

## 6. 人工干预途径（已实施）

| 命令 | 用途 |
|---|---|
| `assign <req_id> version=v1.1.0 iteration=2 depends_on=a,b` | 覆盖自动排期（用户拍板第 2 点） |
| `halt [原因]` / `unhalt` | 暂停/恢复流水线（异常排查防烧 token；唯一暂停方式） |
| `requeue <req_id>` | blocked 从失败阶段续跑（保留已通过阶段） |
| `record_product <req_id> <stage> <产物>` | 合规补记产物（替代手改 status.json） |
| `versions [项目]` | 版本聚合视图 |
| zbot（Telegram） | 全命令透出 + 强制项目确认 |

## 7. 已拍板决策（用户 2026-08-12）

1. **版本号**：语义化（v1.0.0/v1.1.0）；
2. **迭代归属**：自动排（依赖拓扑），`assign` 可覆盖；
3. **变更**：修改→全链重跑该需求 / 删除→忽略 / 新增→按计划跑；
4. **ST**：自动跑（报告供人工抽检，与现有门禁一致）。
