# v2 工程分层模型设计（P1-01 / P1-02 / P1-04 解决方案）

> 状态：**待评审**（用户审后进入实施）
> 目标模型：**项目 → M 版本 → N 需求（依赖关系）→ X 迭代（迭代内并行、迭代间串行）→ UT（需求级）/ IT（迭代级）/ ST（版本级）**
> 设计原则：在现有四态状态机/项目锁/阶段链基础上**增量演进**，不推翻现有已 released 数据。

---

## 1. 现状与差距

| 维度 | 现状（v1） | 目标（v2） |
|---|---|---|
| 版本 | 无（发布说明固定 v1.0.0） | 项目下多版本（v1.0.0/v1.1.0…），需求归属版本 |
| 需求 | 独立全链（分析→方案→…→发布） | 需求有**依赖**（depends_on）与**迭代归属**（iteration） |
| 迭代 | 无 | 版本内 X 个迭代：**迭代内需求并行、迭代间串行** |
| 测试 | 需求级 test 阶段（= UT） | **UT（需求级）→ IT（迭代级）→ ST（版本级）** 三层 |
| 变更 | 无通道（重投新需求） | 变更请求（change request）复用需求修订轮 |

## 2. 数据模型（增量字段）

### 2.1 需求 entry 新增字段（现有 status.json 的 entry 上）

```
"version":    "v1.0.0"              # 归属版本（投放时指定；未指定 → 项目当前开发版本）
"iteration":  2                     # 归属迭代序号（1..X；投放时指定或按依赖自动排）
"depends_on": ["req-b", "req-c"]    # 依赖的需求（先完成才能开始）；空=无依赖
"status":     ...                   # 现有状态机 + 新增 waiting（依赖/迭代前置未满足，等待调度）
```

### 2.2 新增 项目级版本清单 `workspace/<项目>/versions.json`

```json
{
  "versions": [
    {
      "name": "v1.0.0",
      "status": "released",          // planning → in_dev → it → st → released
      "iterations": [1, 2, 3],       // 版本包含的迭代
      "reqs": ["req-a", "req-b"],    // 归属需求
      "released_at": "2026-08-12T..."
    },
    { "name": "v1.1.0", "status": "planning", "iterations": [1], "reqs": [] }
  ],
  "current": "v1.1.0"               // 当前开发版本（新需求默认归属）
}
```

### 2.3 新增 测试分层（状态机扩展）

| 层级 | 触发 | 阶段（新增） | 产物 |
|---|---|---|---|
| **UT** | 每需求 | 现有 test 阶段（= 单元测试，已存在） | `tests/<项目>/<req>...` |
| **IT** | 迭代内全部需求 UT done | 新增 `it` 阶段（it-designer/reviewer） | `it/<项目>/iter-{N}/`（集成测试用例+报告） |
| **ST** | 版本全部迭代 IT done | 新增 `st` 阶段（st-tester/reviewer） | `st/<项目>/v{版本}/`（系统测试报告） |
| 质量评估 | ST 通过后 | 现有 quality/security 门禁（在 ST 后执行） | 现有 |

阶段链（v2）：`req → plan → testplan → code → test(UT) → [迭代门:全部需求UT] → it(IT) → [版本门:全部迭代IT] → st(ST) → quality/security → release`

## 3. 调度约束（迭代间串行 + 需求依赖）

### 3.1 依赖调度（tick 内新增判定）

`find_claimable` 增加前置检查：需求 `status=waiting` 或未满足依赖（`depends_on` 有未 done 需求）→ **不可认领**，等待（不 spawn 不烧 token）。依赖完成后下个 tick 自动可认领。

### 3.2 迭代串行

- 版本内迭代 N+1 的需求，在迭代 N 的**全部需求 UT done + IT PASS** 后才可认领（`waiting` 态等待）；
- **迭代内需求并行**（现有项目锁已天然支持：同项目不同需求由不同 tick 并行认领 ✓）；
- 迭代门（新巡检/调度判定）：迭代全部需求 done + IT PASS → 解锁下一迭代。

### 3.3 版本门

版本全部迭代完成 + ST PASS → 质量/安全门禁 → release → `versions.json` 该版本 released。

## 4. P1-02 需求变更（变更通道）

**方案**：变更请求 = 对已 approved/released 需求的**修订轮**（复用现有 round 机制 + 需求级 requeue 续跑）：

1. **变更入口**：`statectl change_request <req_id> "<变更描述>"` → 需求状态回 `analyzing`（从需求分析重做，**后续阶段按现有 requeue 续跑逻辑只重置受影响阶段**）——**已 delivered 的代码/测试阶段：变更影响评估后决定重跑范围**（v2 简化：需求变更 → 全链从分析重跑该需求，但保留已通过阶段的评审历史作参考）；
2. 变更在 **versions.json 中留痕**（change log：req/时间/描述）；
3. **变更前冻结**：需求 released 后若所属版本已 released → 变更需先开**新版本**（v1.1.0）承载，不修改已发布版本（版本不可变原则）。

## 5. 实施分期（每期独立验证+提交）

| 期 | 内容 | 涉及 |
|---|---|---|
| **1（P1-01）** | 版本概念：需求加 `version` 字段 + `versions.json` + 版本聚合视图（`statectl versions`）+ 版本 released 状态 | statectl.py + install/uninstall 骨架 + 文档 |
| **2（P1-04 核心）** | 依赖（depends_on）+ waiting 态 + 调度约束（tick 前置检查） | statectl.py next_action/find_claimable/tick |
| **3（P1-04 迭代）** | 迭代归属 + 迭代门（迭代内全 UT+IT PASS 解锁下一迭代）+ 迭代间串行 | statectl.py + 巡检 |
| **4（P1-04 测试分层）** | it/st 新阶段 + 角色文件（it-designer/it-reviewer/st-tester/st-reviewer）+ 阶段链接入 | statectl.py STAGES + roles/ + 文档 |
| **5（P1-02）** | change_request 命令 + 变更冻结（版本不可变）+ change log | statectl.py + zbot 干预命令 |
| **6** | 文档/skill/zbot 全量同步 + 端到端验证（真实版本流程） | 全部资产 |

## 6. 兼容与迁移

- **存量 4 项目**（snake-linux/tetris/pacman/gomoku 已 released）：迁移 = 补 `version: "v1.0.0"` + 归入 versions.json（已 released 版本）——**零状态机改动，只补元数据**；
- 新投放需求：默认归属 `versions.json` 的 `current` 版本；
- 现有阶段链/四态/项目锁/巡检**全部保留**（v2 是**增量**：新增字段 + 新增阶段 + 调度约束）；
- 旧命令完全兼容（不指定 version/iteration/depends_on 时行为同 v1）。

## 7. 待确认点（评审时请拍板）

1. **版本号策略**：语义化（v1.0.0）vs 简单递增（v1/v2）？→ 建议语义化；
2. **需求迭代归属**：投放时用户指定，还是自动排（按依赖拓扑排序）？→ 建议**自动排 + 可覆盖**；
3. **变更重跑范围**：需求变更默认全链重跑该需求（保留评审历史），还是智能只重跑受影响阶段？→ 建议一期先全链（简单可靠），后续优化；
4. **ST 是否必须人工参与**：ST（系统测试）由 worker 自动跑 vs 需要人工确认后放行？→ 建议**自动 + ST 报告供人工抽检**（与现有门禁一致）。
