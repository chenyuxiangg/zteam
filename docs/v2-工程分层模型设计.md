# v2 工程分层模型设计（模块中心版）

> 状态：**设计定稿**（用户 2026-08-12 拍板 6 点）——已实施部分（版本/依赖/waiting/IT-ST 骨架）保留复用，开发组织模型重构为**模块中心**
> 目标模型：**项目 → M 版本 → N 需求规格（权威需求）→ 架构师一次性架构设计 → 模块（1 开发者+1 测试者）→ 迭代开发（TDD）→ 版本级 ST → 发布**

---

## 0. 模型总览（用户 2026-08-12 拍板）

```
需求请求（input 草稿，可模糊，永不覆盖）
   ↓ 需求分析师细化（规格 = 权威需求；模块划分与用户对齐）
需求规格（approved analysis）—— 开发的起点
   ↓
【架构师】版本级一次性：架构设计（开发架构 + 技术选型 + 需求→模块分发 + 迭代计划）
   ↓ 架构评审
【模块】（项目稳定组织单元：基础平台 / 中间件 / 上层应用，项目可自定义）
   ↓ 每次迭代（架构师迭代计划）
【模块开发者】迭代方案设计（功能模块设计）→ 评审
   ↓ TDD 开发 → 模块代码 + 模块 UT（模块级交付物）→ 评审
【模块测试者】模块 IT（集成测试）→ 评审
   ↓ 版本全部迭代完成
【测试承担】版本级 ST（系统集成）→ 评审 → 质量/安全门禁 → 版本 release
```

## 1. 核心决策（用户拍板 2026-08-12）

1. **架构设计粒度**：版本级一次性（覆盖该版本全部需求）；
2. **模块**：项目内**稳定组织单元**，三类（基础平台/中间件/上层应用），**项目可自定义**（需求分析师与用户对齐模块划分）；
3. **UT**：**模块级交付物**（开发者 TDD 产出，评审）；
4. **ST**：版本级保留，**系统集成由测试承担**；
5. **需求开发全部下沉到模块**：需求不再有独立 code/test 阶段；
6. **评审铁律**：只要有交付物，一定有评审者（沿用当前模式）。

## 2. 数据模型

### 2.1 需求 entry（status.json）

```
status: pending → analyzing → analyzed → reviewing（AI 预审，仅质量提示不拍板）
        → awaiting_user_confirm（用户评审：规格推送给用户拍板）→ approved（用户确认=规格锁定）
        → assigned（已分发给模块）/ waiting（等架构设计）
        → released（所属模块 IT 通过、版本发布时）
version/iteration/depends_on：保留（迭代由架构师计划，depends_on 供架构师参考）
source: input 草稿路径（显式记录）；spec: analysis 路径（=需求规格）
```

> **用户评审铁律（2026-08-12）**：需求规格的最终评审由**用户**拍板——
> 分析师细化 → AI 预审（req-reviewer 仅做完整性/矛盾检查，输出问题清单，**不通过/不否决**）
> → zbot 推送规格摘要 → 用户确认（`confirm <req_id>` → approved）或驳回（`reject <req_id> <理由>` → 重细化）。
> 用户不确认则规格挂起（不自动通过）；zbot 定期提醒未确认规格。

### 2.2 模块（新增，项目级 modules.json）

```json
{
  "modules": [
    {"name": "platform-core", "type": "基础平台",   "desc": "…",
     "depends_on": [],                       // 模块依赖：依赖的模块 it_passed 后本模块才可调度（迭代内串行）
     "reqs": ["req-a", "req-b"],            // 架构师分发的需求
     "iterations": [{"n": 1, "status": "design_pending", "design_product": null, "dev_product": null, "ut_product": null, "it_product": null, "reviews": {}}],
     "status": "pending"}                    // 模块级状态机（跨迭代）
  ]
}
```

模块状态机（per 迭代）：`design_pending → design_reviewing（功能模块设计+评审）→ dev_working（TDD 开发+UT）→ dev_reviewing → it_working（模块 IT）→ it_passed`；失败打回重做。

**调度规则（2026-08-12）**：迭代内**无依赖的模块并行**（同时开发）；**有依赖的模块串行**（依赖模块 it_passed 后才开始本模块）。

### 2.3 版本（versions.json，已实施 + 扩展）

```
架构设计产物：architecture（版本级，架构师产出+评审通过）
迭代计划：架构师制定（iterations 列表 = 模块 × 迭代 排期）
版本状态：planning → arch_done（架构设计完成）→ in_dev → st_pending → st_passed → quality_pending → released
```

## 3. 阶段链（重构：需求级下沉到模块）

| 层级 | 流程 | 交付物（必有评审） |
|---|---|---|
| **需求级** | 细化 → 评审 → 规格锁定 | 需求规格（analysis）|
| **版本级** | 架构设计 → 评审 | 架构设计（架构/选型/需求→模块/迭代计划）|
| **模块级**（per 迭代） | 功能模块设计 → 评审 → TDD 开发 → 评审 → 模块 IT → 评审 | 模块设计 / 模块代码+UT / 模块 IT 报告 |
| **版本级** | 系统集成 ST → 评审 → 门禁 → 发布 | ST 报告（测试承担）/ 发布包 |

## 4. 角色重构（有交付物必有评审）

| 角色 | 职责 | 说明 |
|---|---|---|
| 需求分析师 / 需求评审者（AI 预审） | 细化规格（+模块划分对齐）/ AI 预审（质量提示） | 预审不拍板 |
| **用户（评审终审）** | 规格确认/驳回（zbot：confirm/reject） | **规格唯一拍板人** |
| **架构师** / 架构评审者 | 版本级架构设计 / 评审 | dev-plan-designer 改造 |
| **模块开发者** / 模块开发评审者 | 迭代方案设计 + TDD 开发 + 模块 UT / 评审 | code-developer 改造（按模块）|
| **模块测试者** / 模块测试评审者 | 模块 IT / 评审 | test-developer 改造 |
| **系统集成测试**（测试承担）/ ST 评审者 | 版本级 ST / 评审 | it/st 角色演进 |
| 质量/安全门禁、发布者 | 版本级门禁与发布 | 保留（版本级）|

## 5. 调度（tick，机制沿用 + 模块/版本级扩展）

```
tick（每项目锁内）：
1. register 需求请求 → 分析（等待细化）
2. 需求 approved → 等架构设计（waiting）
3. 版本 planning 且需求全 approved → 架构师 spawn（架构设计）
4. 架构评审 PASS → 架构师分发：需求→模块、迭代计划落盘（modules.json）
5. 迭代计划执行：模块 per 迭代 状态机（设计→评审→TDD→评审→IT→评审）；
   迭代内**无依赖模块并行**（同时推进），**有依赖模块串行**（依赖模块 it_passed 后解锁，复用 waiting 机制）
6. 版本全部迭代完成 → ST（测试承担）→ 门禁 → release
```

## 6. 变更（P1-02，沿用三分场景）

- 修改：change_request → 重新细化规格（草稿/旧规格留档）→ 重新分发/重跑；
- 删除：忽略该需求（模块/版本移除，依赖解锁）；
- 新增：投放草稿 → 细化 → 架构师下次架构迭代纳入；
- 版本冻结：released 版本不可改。

## 7. 兼容与迁移

- 存量 4 项目：released 数据保留；模块化迁移 = 按需建立模块映射（分析师/用户对齐）；
