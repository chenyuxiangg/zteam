# v2 流水线设计（模块中心版）—— 设计评审稿 v1.0

> 依据：用户《设想的流程.md》+ 2026-08-12 逐项拍板（8 问 8 答）
> 状态：**待用户评审**（评审通过后才进入开发）
> 范围：本设计替代现有"需求独立全链"模型，开发组织重构为 **PM/SE/TE/MDE/FO/MTO/STO/QA 八角色 + 模块中心**；版本/项目/锁/巡检/命令框架等既有机制保留复用。

---

## 0. 设计原则

1. **需求规格是开发起点**：input 草稿（可模糊，永不覆盖）→ PM 细化 → **用户评审** → 规格锁定；
2. **模块是开发平台**：需求按模块分发，模块 = 1 设计者(MDE) + 1 开发者(FO) + 1 测试者(MTO) 的协同单元；
3. **评审铁律**：有交付物必有评审（评审人见 §6 映射表）；
4. **版本串行**：同一项目同时只有 1 个活跃版本；当前版本 release 后才能开下一个；
5. **迭代控制**：先最小闭环再增量；依赖决定串行，无依赖并行；模块可跨迭代；
6. **质量闭环**：代码检视是门禁；问题单由提单人复测关闭；
7. 在现有机制上**增量演进**（项目锁/四态/巡检/命令框架复用），存量数据兼容。

### 0.1 机制守护铁律（AI 不自保证）⚠️ 最高优先

> **状态记录、状态转移、文件落盘确认——一律由脚本固定规则守护，AI 不自保证。**

**AI（worker）只被允许做两件事**：
1. **产出内容**：写产物文件（分析/设计/代码/测试/报告…）；
2. **调用状态命令**：`statectl` 的固定命令（set_status/release_*/confirm…）——**仅此而已**。

**AI 永远不被允许**：直接写 status.json/modules.json/versions.json、跳过校验、自称"已完成"。

**脚本守护规则（状态判定全部由代码执行，不信 AI 自述）**：

| # | 守护点 | 固定规则（statectl.py 代码强制） |
|---|---|---|
| 1 | **迁移表** | 合法状态转移白名单（如 pending→analyzing→analyzed→awaiting_user_confirm→approved…）；非法转移直接拒绝返回非 0 |
| 2 | **落盘确认** | AI 声称"产物已写"无效——release_* 命令**校验产物真实存在**（路径/目录/文件）+ **内容合规**（结论区 PASS/FAIL 在头部 N 字符内、非空）后才迁移状态 |
| 3 | **认领防重** | find_claimable 未认领过滤 + claimed_by/claimed_at/worker_pid + pid_alive 进程存活检测；已认领不可重复认领/双 spawn |
| 4 | **锁** | 全局锁 + 项目锁（flock）；一切状态读写原子串行 |
| 5 | **原子写盘** | tmp + os.replace（防半写/撕裂） |
| 6 | **巡检兜底** | 每 5 分钟按固定规则自动补正：AI 漏设状态→（产物存在+结论合规→补正）；worker 进程死亡→stale 恢复；**不依赖 AI 自觉** |
| 7 | **审计** | 一切状态变更自动写 pipeline.log + timeline/state_since；可回放可追溯 |
| 8 | **问题单门禁** | open 问题单数 > 0 → 脚本拒绝模块/版本进下一阶段 |
| 9 | **版本串行** | 迁移表强制：新版本 arch 前置 = 当前版本 released |
| 10 | **结论解析** | parse_conclusion 固定规则解析结论区（不靠 AI 口头结论） |

**AI 谎报/漏报的后果由脚本兜住**：漏设状态 → 巡检补正（GUARD 审计）；错误落盘 → 命令校验拒绝；进程崩溃 → stale 恢复。**可靠性由规则保证，不由 AI 态度保证**。

## 3. 数据模型

### 3.1 项目（workspace/{项目}/，既有）

项目锁/全局锁/目录分层保留；多项目并行。

### 3.2 版本（versions.json 扩展）

```json
{ "versions": [
    {"name": "v1.1.0",
     "status": "planning",        // planning → arch → in_dev → st → qa → released（串行：同项目仅 1 活跃）
     "architecture": null,         // 架构设计产物（SE，PM 评审后生效）
     "module_plan": null,          // 功能模块分工表（SE，PM 评审后生效；含迭代计划）
     "test_plan": null,            // 整体测试方案（TE，SE 评审后生效）
     "st_product": null, "st_report": null,
     "qa_report": null, "release_pkg": null,
     "released_at": null}],
  "current": "v1.1.0" }
```

### 3.3 模块（modules.json，项目级，SE 抉择组织形态）

```json
{ "modules": [
    {"name": "platform-core", "type": "基础平台", "desc": "…",
     "depends_on": [],              // 模块依赖（SE 架构设计定）：依赖模块 it_passed 后本模块可调度
     "reqs": ["req-a"],             // SE 分发的需求规格
     "design": {"product": null, "reviews": []},      // 模块设计文档（迭代内复用）
     "iterations": [{"n": 1, "phase": "design", "status": "pending",   // 模块×迭代 状态
                     "dev_product": null, "ut_product": null,
                     "it_product": null, "it_report": null, "it_reviews": []}],
     "alive": true}] }              // false = SE 抉择下线（老模块退役，需求改分发）
```

模块状态（per 迭代）：`design_pending → design_reviewing → dev_working → dev_reviewing（检视门禁）→ it_working → it_passed`；任一评审/检视不通过 → 打回对应态重做。**模块可跨迭代**（下一迭代继续承担新需求）。

### 3.4 需求（status.json entry，演进）

```
status: pending → analyzing → analyzed → awaiting_user_confirm → approved（规格锁定）
        → dispatched（SE 已分发到模块）→ released（所属模块 it_passed 且版本发布）
        （reviewing 态=AI 预审仅质量提示，不拍板）
version/iteration/depends_on/source/spec：保留（depends_on 供 SE 架构设计参考）
```

### 3.5 问题单（问题单 = 复用 failures/轮次机制，新增问题单文件）

```
问题单：workspace/{项目}/issues/{req_id 或模块}/issue-{N}.md
  内容：提单人（MTO/STO）、严重级、描述、期望行为、状态（open → fixing → fixed → closed）
  闭环：FO 修复（fixed）→ 提单人复测（通过 → closed / 不通过 → 重新 open）
  状态机挂钩：问题单 open 数 > 0 时模块/版本不能进入下一阶段（门禁条件）
```

## 4. 状态机

| 层级 | 状态链 |
|---|---|
| **需求** | pending → analyzing → analyzed → awaiting_user_confirm → approved → dispatched → released（版本发布时）；blocked（failures≥2/轮次超限，人工 requeue） |
| **模块（per 迭代）** | design_pending → design_reviewing → dev_working → dev_reviewing（检视门禁）→ it_working → it_passed；打回重做；跨迭代延续 |
| **版本** | planning → arch（架构评审中）→ in_dev（模块迭代循环）→ st → qa → released；同项目仅 1 活跃（release 后开新版本） |
| **问题单** | open → fixing → fixed → closed（提单人复测） |

## 5. 调度过程（tick 每 5 分钟 × 每项目锁内）

```
1. register：input 草稿 → PM 细化队列（规格未锁定前 PM 可多轮细化）
2. PM 细化完成 → awaiting_user_confirm → zbot 推送 → 用户 confirm/reject（reject → 重细化）
3. 规格全部锁定 → SE 架构阶段：spawn SE（架构设计+模块组织+分发+迭代计划）
   → PM 评审架构 → 通过 → 落盘 modules.json（模块/依赖/需求分发/迭代计划）+ 版本 arch_done
4. TE 测试方案（SE 评审后生效）
5. 迭代执行（版本 in_dev）：按 SE 迭代计划调度模块——
   - 模块迭代设计：MDE（模块设计）→ SE 评审 → design PASS
   - FO TDD 开发（代码+UT 自闭环）→ MDE/SE 检视门禁（检视意见文件；不通过→巡检唤醒 FO 修改）
   - MTO 用例（TE 评审通过后写代码）→ 模块 IT → it_passed（问题单闭环后）
   - 迭代内无依赖模块并行（多 worker）；依赖模块等前置 it_passed
6. 全部迭代完成 → 版本 st：STO 用例（TE 评审）→ ST → 集成测试报告 + 问题单闭环
7. QA：评审测试报告 + 安全红线 + 用户指南（用户评审）→ release 包 → 版本 released
8. 版本 released → 允许开新版本（串行约束）
```

## 7. 关键机制设计

### 7.1 代码检视门禁
- MDE/SE 检视意见以**文件**落盘（`{项目}/code/{模块}/review-{轮次}.md`）；
- 检视不通过 → 模块状态打回 dev_working（或等待态）+ **巡检唤醒 FO**（spawn FO 阅读意见文档并修改）；
- 复检通过 → 进入 it 阶段。

### 7.2 问题单闭环
- 提单（MTO/STO）→ open；FO 修复 → fixing → fixed；**提单人复测** → closed；
- 模块/版本存在 open 问题单时**不能进入下一阶段**（门禁条件）；
- 复用 failures/轮次机制：问题单累计或修复失败达阈值 → blocked。

### 7.3 迭代控制（SE 排期）
- 迭代存在的两个理由（用户定义）：a. 先最小闭环再增量，控制多需求代码质量风险；b. 依赖（模块内/模块间）必须先完成被依赖项；
- 有依赖的迭代串行，无依赖的迭代/模块并行；模块可跨迭代（同一模块多轮迭代增量开发）。

### 7.4 版本串行
- 同项目同时仅 1 个活跃版本（in_dev/st/qa 态）；新版本 planning 可提前建（仅规划），**arch 起需当前版本 released**。

### 7.5 PM 细化方法论
- PM 角色文件注入：麦肯锡理论（MECE/金字塔原理）+ 网络查询能力（hermes web 工具）；
- 输出规格结构：背景/目标/功能需求/非功能需求/边界/验收标准（用户可评审的形态）。

## 8. 变更管理（P1-02，沿用三分场景）

| 场景 | 处理 |
|---|---|
| 修改需求 | change_request → 重细化规格（草稿/旧规格留档）→ 用户评审 → 重新分发/重跑该需求（影响模块检视/IT） |
| 删除需求 | 忽略该需求（模块/版本移除；依赖它的需求/模块解除阻塞） |
| 新增需求 | 投放草稿 → 细化 → 用户评审 → SE 下次架构迭代纳入（或增补分发） |
| 版本冻结 | released 版本不可修改；变更开新版本承载 |
