# 机制设计与上线规范（zteam）

> 2026-09-11 制定。背景：v1.0.0 期间出现 **3 次"机制半通"**（新机制只验证前半段就上线，后半段被门禁挡死/无触发点），
> 造成版本静默停滞与多轮空转。本规范把"机制怎么设计、怎么上线、怎么验证"固定下来。

---

## 1. 触机三要素（每个机制必须声明，缺一不可）

| 要素 | 含义 | 反例（不可接受） |
|---|---|---|
| **触发点** | 何时被触发：命令入口 / tick 巡检 / 状态迁移 / 门禁 | "AI 想起来时" |
| **触发者** | 谁触发：调度器（tick）/ 命令入口 / worker | "某个人记得跑" |
| **兜底** | **没触发怎么办**：巡检补正 / 告警 / 拒绝流转 | 无（静默停滞）|

**优先级规则**：能挂**命令入口**或**tick 巡检**的，绝不依赖"AI 自觉"；
需要语义判断的（根因归属、判据可达性、拒修理由）才交给 AI，且**必须配机制校验其产物**
（例：拒修 → 必须有 `reject` 记录；读进度 → 必须有进度文件）。

---

## 2. 上线下四步（缺一不可）

1. **端到端回路验证**：不只测单点——把"触发 → 执行 → 状态流转 → 后续环节"整条链跑一遍。
   *教训*：SE 分单 + 再激活上线时只验了"分单→挂载"，没验"再激活后 FO 派单"（被 `in_dev` 门禁挡死）。
2. **结构不变式**：把该机制要求"永远成立"的约束写成断言，进 `diagnose`（D 系列）**且**每 tick 幂等自愈。
   *样板*：D17「存在进行中迭代 ⇒ 版本必须 in_dev」+ `VERSION_REOPEN` 自愈。
3. **回归检查**：确认不破坏既有流程（旧路径必须保留默认行为）。
   *样板*：复测方按提单人分派时，MTO 路径原样保留为默认分支。
4. **文档/skill 同步**：`docs/` + `roles/` + `skill`（**工作区与 `~/.hermes` 两边一致**，diff 复核）。

---

## 4. 随机触发黑名单（禁止）

- ❌ "靠 worker 自觉读进度/写证据"——必须有机制校验产物存在性；
- ❌ "靠人记得跑检查"——必须挂命令入口或 tick；
- ❌ "靠 AI 判断后自行处理"——必须把结果落成可检查的状态（文件/字段/命令记录）。

---

## 5. 机制改动审计要求

每次机制改动必须在 `logs/pipeline.log` 留下可检索记录（`log()` 调用），且改动说明包含：
`触发点 / 触发者 / 兜底 / 回路验证方式`（四要素齐备才允许提交）。
