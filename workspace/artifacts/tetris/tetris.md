## 需求原文

# 需求：Linux 终端版俄罗斯方块游戏（Python 从零实现）

**投放时间**：2026-08-08
**来源**：Telegram 用户直接投放
**项目**：tetris

## 需求描述

开发一个运行于 **Linux 终端**的俄罗斯方块（Tetris）游戏，使用 Python 从零实现，不依赖第三方游戏框架。

## 期望要点（供分析师展开）

- **纯终端**：TTY 环境运行，非 TTY 给出明确报错；单命令启动（如 `python3 tetris.py`）
- **从零实现**：核心玩法只用 Python 标准库，不套用现成游戏框架
- **经典玩法**：7 种标准方块（I/O/T/S/Z/J/L）、下落/左移/右移/旋转/硬降（hard drop）/软降（soft drop）
- **消行机制**：整行填满消除、计分规则（如 1/2/3/4 行不同分值）、等级随消行提升、速度随等级加快
- **游戏控制**：WASD 或方向键 + 空格（硬降）+ P（暂停）；撞顶（堆叠到顶部）判定游戏结束
- **预览与信息**：下一个方块预览（next）、当前得分/等级/消行数显示（HUD）
- **退出干净**：恢复终端原始状态（光标、回显、颜色），Ctrl+C 安全中断
- **技术选型**：Linux 下 curses 与裸 ANSI 转义序列的取舍论证（参考 snake-linux 已通过的分析结论）
- **交付 README**：运行方式、依赖、键位表、配置（如 tick 间隔/颜色开关）、已知限制

## 验收标准（待评审确认）

- Linux 终端可玩、控制流畅（下落 tick 无感知延迟，按键响应及时）
- 7 种方块旋转、消行、计分、等级提升均正确
- 代码职责分离、每个源文件可读性良好
- 按 README 在干净 Linux 环境可跑通

## 1. 需求理解（SCQA）

### 1.1 情境（Situation）
需求方是工程背景的独立开发者，此前已在流水线中投放并通过了「Linux 终端贪吃蛇」需求（snake-linux，已 released 归档）。本需求是同一思路的延续：再次要求一个 **Linux 终端 + Python 从零实现 + 仅标准库** 的经典游戏，本次为俄罗斯方块（Tetris）。需求原文已给出相当具体的期望要点：7 种标准方块、下落/移动/旋转/硬降/软降、消行计分、等级与速度、键位方案、next 预览、HUD、干净退出、README 交付，并明确点名「技术选型（curses vs 裸 ANSI）的取舍论证参考 snake-linux 已通过的分析结论」。需求方最终目标是可运行、可玩、可维护的终端游戏成品。

### 1.2 冲突（Complication）
俄罗斯方块看似经典简单，但「从零实现」要面对的细节远比贪吃蛇复杂：7 种方块（I/O/T/S/Z/J/L）各自的形状矩阵与旋转表现、消行判定与计分、等级与速度联动、堆叠与锁定、撞顶结束——这些规则若不在需求层规格化，实现阶段必然出现口径分歧。同时终端程序有与 snake-linux 相同的质量陷阱：退出后终端状态（光标/回显/颜色）未恢复会破坏体验，非 TTY 环境运行会报晦涩错误。此外，需求原文「期望要点」中的技术选型论证（curses vs ANSI）与分析师「只答 What/Why、不答 How」的红线存在冲突——snake-linux 评审已就同类问题达成结论（论证属 How、由实现阶段负责、README 记录选型理由），本需求沿用该结论（见 §2.2 末段与 Q-09）。

### 1.3 问题（Question）
如何将「Linux 终端 + Python 标准库从零实现的经典俄罗斯方块」这一原始需求，分解为结构完整、边界清晰、验收可测的功能需求与非功能需求，供评审确认与后续实现对齐？

### 1.4 结论（Answer）
本需求的核心价值是：交付一个 **零第三方依赖、单命令启动、干净退出、经典可玩** 的 Linux 终端俄罗斯方块（Python 实现），以「从零实现 + 完整 README」兼具玩具趣味与教学参考价值；本分析文档将该价值固化为 26 项编号 FR（其中 FR-17/FR-26 为待拍板可选项）与 6 项可度量的 NFR，并把规则细节中的不确定性（计分数值、旋转系统、随机策略、场规格等）显式列入待确认问题，不替需求方拍板。本轮针对评审 5 条意见完成逐条处理：tick 相关验收全部绝对值化、旋转验收增加前置基线、技术选型论证从「不做什么」移出并独立声明、NFR 性能指标标注为建议项、新增 tick 术语定义。

## 2. 需求范围（MECE 边界）

### 2.1 做什么
- 在 Linux 终端（TTY）内运行的俄罗斯方块游戏，Python 实现，仅使用标准库；
- 经典玩法闭环：7 种标准方块（I/O/T/S/Z/J/L）、下落/左移/右移/旋转/软降/硬降、整行消行、计分、等级与速度联动、撞顶结束；
- 游戏区域边界明确：可见边框标示、方块坐标不出界（见 FR-06、FR-20）；
- 游戏界面：next 方块预览 + 得分/等级/消行数 HUD（见 FR-21、FR-22）；
- 单命令启动、tick 间隔可配置；
- 干净退出：恢复终端原始状态（光标、回显、颜色），Ctrl+C 安全中断；
- 交付 README：运行方式、依赖、键位表、配置项、已知限制；
- 非 TTY 环境下给出明确报错而非晦涩异常。

### 2.2 不做什么
- 不做图形界面/浏览器/移动端版本（平台明确限定 Linux 终端）；
- 不做 Windows/macOS 平台适配（curses 跨平台兼容与 windows-curses 等不在范围内，需求方在 snake-linux 中已明确同类边界）；
- 不做网络对战、多人模式、排行榜服务器等联网能力（对照竞品 vitetris 的 netplay 特性，明确排除）；
- 不做音效、动画特效等多媒体能力；
- 不做第三方游戏框架/引擎集成（需求方明确「从零实现」）；
- 不做游戏开局/换方块的「运气干预」机制（对照竞品 bastet 的「故意给最差方块」玩法，明确排除，见 §5）。

**关于「技术选型论证（curses vs 裸 ANSI）」的独立说明（对应 R1-03，从本列表移出）**：该论证是需求原文明确要求的交付物，不属于「不做什么」，其归属问题是**由谁做、以什么形式交付**，而非是否要做。本分析按 snake-linux 已通过评审的正式口径处理：
1. 论证的**决策约束**已固化为可验证需求：仅 Python 标准库（FR-01、§6 依赖）、纯 TTY（FR-02）、干净退出（FR-23、NFR-03）、终端卫生（NFR-04）——无论实现选 curses 还是 ANSI 都必须满足，论证不改变这些约束；
2. 论证工作本身超出本分析角色职责（属 How），**推荐**由实现阶段完成，并在交付物 README「已知限制」中记录选型理由与取舍结论；
3. 若需求方坚持该论证必须作为独立交付物，可另提「技术方案分析」类任务，或调整为评审口径（三选一，见 Q-09）。

## 3. 功能需求（FR，MECE 分组）

**术语定义（对应 R1-05，新增）**：**tick = 游戏主循环每次迭代的时间间隔，即自动下落一格的最小时间单位（= 当前下落速度）**。tick 可配置（FR-03，建议默认 500ms，见 Q-04），与渲染帧率无关。本文档中凡出现「tick」均指此定义；涉及误差/响应时间的验收一律使用绝对值（毫秒/P95），不使用 tick 作为度量单位（对应 R1-01）。

分组维度声明：按**游戏生命周期阶段**（启动初始化 → 方块生命周期 → 消除与计分 → 输入控制 → 界面显示 → 结束清理 → 交付物）归组，各阶段互不重叠、合起来覆盖「从启动到退出」的完整用户旅程。编号自 r1 起保持稳定，本轮无新增条目。

### 3.1 启动与初始化
| 编号 | 功能点 | 描述 | 优先级 | 验收标准 |
|------|--------|------|--------|----------|
| FR-01 | 单命令启动 | 在 Linux 终端执行单一命令（如 `python3 tetris.py`，文件名以交付为准）即进入游戏，无需安装任何第三方包 | 高 | 在干净 Linux 环境中执行启动命令，游戏界面 3 秒内出现，无报错。**「干净 Linux 环境」定义**（沿用 snake-linux FR-01）：仅预装系统自带 Python 3.x 与标准库、无任何第三方包、无游戏相关自定义配置（别名/环境变量）的常见发行版（Ubuntu/Debian/Fedora/Arch 之一） |

| FR-04 | 终端能力检查 | 启动时检测终端尺寸是否满足最低可玩要求（游戏区域 + 信息栏 + 边框），不满足时给出可读提示 | 中 | 在小于游戏区域所需尺寸（见 FR-20/Q-10）的终端中启动，输出可读提示且不产生乱码界面 |

### 3.2 方块生命周期
| 编号 | 功能点 | 描述 | 优先级 | 验收标准 |
|------|--------|------|--------|----------|
| FR-05 | 七种标准方块 | 提供 I/O/T/S/Z/J/L 七种标准俄罗斯方块，每种有确定的形状与旋转表现 | 高 | 游戏运行中 7 种方块均可出现；每种方块形状与标准定义一致（I=直四格、O=田字、T/S/Z=三连拐、J/L=L 形），无缺失或变形方块 |
| FR-06 | 方块生成与活动区 | 当前方块在游戏区域顶部生成并开始下落；游戏区域为固定尺寸画布（尺寸待 Q-10，建议 10 列 × 20 行，对齐行业标准），方块坐标恒在区域内 | 高 | 新方块生成于区域顶部中央且在边界内；任意时刻活动方块与已堆叠方块的坐标均在区域边界内，无越界绘制 |
| FR-07 | 自动下落 | 活动方块按 tick 间隔自动下落一格 | 高 | 不操作输入时，方块每 tick 下落 1 格，方向与速度保持不变；**实际下落间隔与配置值偏差 ≤ max(50ms, tick×5%)**（对应 R1-01）；下落频率与当前等级/配置一致（见 FR-14） |
| FR-08 | 左移/右移 | 活动方块可左移/右移一格 | 高 | 按左移键方块左移 1 格、右移键右移 1 格；方块一侧已抵堆叠方块或边界时，该方向移动被拒绝且方块不消失、不越界 |
| FR-09 | 旋转 | 活动方块可旋转（顺时针/逆时针至少一种方向，方向集待 Q-02 拍板） | 高 | 按旋转键方块旋转 90°；旋转后若与堆叠方块/边界重叠则旋转被拒绝且方块保持原姿态。**前置条件（对应 R1-02）：在 Q-02 旋转规则确定前，本项以「顺时针 90°、旋转重叠即拒绝（无墙踢）」为临时验收基线（与 Q-02 建议默认一致）；若需求方选定 SRS（含墙踢表）或其它规则，需同步更新本项验收标准** |
| FR-10 | 软降（soft drop） | 按住软降键时方块加速下落（逐格快速下落） | 中 | 按住软降键期间方块下落速度 ≥ 自动下落速度 ×4（默认 tick 500ms 下即 ≤125ms/格）；松开后恢复自动下落速度（对应 R1-01 绝对值化） |
| FR-11 | 硬降（hard drop） | 按硬降键时方块立即下落到底部并锁定 | 高 | 按硬降键后方块瞬间落至当前列最低可落位置并锁定，耗时 < 100ms（自按键起至画面更新止）；锁定的方块立即参与消行判定（见 FR-15） |
| FR-12 | 方块锁定与堆叠 | 方块落至底部或堆叠方块之上时锁定为该列的静态方块，并生成下一个新方块 | 高 | 方块触底/触堆叠后立即锁定，锁定位置与下落路径一致（无穿墙/穿透堆叠）；**锁定后 ≤100ms 内新方块生成并开始下落**（lock delay 是否引入见 Q-03） |
| FR-13 | 撞顶结束判定 | 方块堆叠至顶部（新方块生成位置被占用）时游戏结束 | 高 | 当新生成方块与堆叠方块重叠（生成位置被占用）时，游戏进入结束状态（见 FR-24），不再继续下落 |

### 5.3 差异化机会
1. **机会：零依赖 + 单命令启动**。vitetris 需编译、tetris-bsd 需 apt 安装，本需求「纯标准库 + `python3 tetris.py`」把运行门槛降到最低，适合极客尝鲜与教学场景（来源：vitetris README 需编译运行、本需求原文明确标准库约束）。
2. **机会：终端卫生（干净退出）作为一等公民**。显式要求恢复光标/回显/颜色、非 TTY 友好报错，这一质量维度在多数开源终端游戏中未被系统化承诺，是差异化卖点（来源：需求原文明确约束；对照竞品仅依赖 curses 库自身清理）。
3. **机会：从零实现的教学参考价值**。代码职责分离、可读性好、README 完整，可作为「用 Python 标准库写终端游戏」的进阶范例（比贪吃蛇更复杂：旋转矩阵/消行/计分联动）——这是 C 竞品难以直接提供的价值（来源：需求原文验收标准）。
4. **风险：功能丰富度远低于竞品**。vitetris 的 netplay、双人模式、外观定制、B 型玩法均不在本需求范围（见 2.2），若需求方后续扩展预期未管理好，会形成「功能少」的观感；需在评审中确认功能边界（来源：vitetris README 特性列表）。
5. **风险：规则口径分歧**。旋转系统（SRS 与否）、wall kick、lock delay、计分数值、随机策略（7-bag vs 纯随机）是俄罗斯方块社区的经典分歧点，若不拍板，实现与验收会各执一词——本分析已将其全部列入待确认问题（Q-01~Q-03），需评审确认（来源：Tetris Wiki Guideline/SRS 页面所述规则差异）。
