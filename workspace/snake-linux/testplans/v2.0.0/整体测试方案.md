# 整体测试方案：snake-linux v2.0.0（snake-gui）

> TE 产出 · 依据架构设计 `arch/v2.0.0/架构设计.md`、功能模块分工表 `arch/v2.0.0/功能模块分工表.md`、需求规格 `analysis/snake-gui-r1.md`（approved）
> 对齐验收标准 1~7（§规格验收标准）；测试套件框架详见同目录《测试套件框架设计.md》

## 0. 版本与范围速览

| 项 | 内容 |
|----|------|
| 项目 / 版本 | snake-linux / v2.0.0（单需求 snake-gui，独立于已 released 的终端版 v1.0.0） |
| 模块清单 | game-core（基础平台，迭代 1,2）、platform-storage（中间件，迭代 2）、gui-renderer（中间件，迭代 1,3）、game-app（上层应用，迭代 1,2,3,4） |
| 依赖链 | gui-renderer → game-core；game-app → game-core/gui-renderer/platform-storage；core/storage 无依赖（叶子） |
| 技术栈 | Python 3.8+ / Pygame(SDL2) / PyInstaller 单文件；core+storage 纯标准库零 GUI 依赖（NFR-05） |
| 交付形态 | 三平台免安装单文件可执行（FR-14）+ SHA256SUMS + 发布说明 + 用户指南（FR-16） |
| 测试层级 | UT（模块内单元）→ IT（模块级集成，MTO 执行）→ ST（版本级端到端，STO 执行）；TE 不执行测试 |

## 1. 测试目标与分层策略

**总体策略**：按架构三层（core 纯逻辑 / storage 中间件 / renderer+app GUI 装配）分层测试——
1. **core/storage 层全部自动化**：纯标准库可脱离 GUI 做确定性测试（NFR-05 保证的天然挂载点），覆盖玩法逻辑、难度参数、持久化边界；
2. **renderer 层 headless 自动化 + 截图留档**：SDL dummy 驱动下做渲染确定性断言（帧内容/皮肤差异/缩放），视觉观感由 ST 人工验收；
3. **app 层事件注入自动化 + 打包产物人工验收**：用合成事件驱动主循环验证流程状态机；单文件可执行与三平台矩阵属 ST 人工/半自动验收。

**需求覆盖口径**：FR-01~16 与 NFR-01~07 全部进入测试矩阵（无范围外需求——本版本所有 FR/NFR 均为确定项）；映射见 §4。

## 2. IT 方案（模块级，MTO 执行）

### 2.1 模块 × 迭代 IT 范围

| 模块 | 迭代 | IT 范围（接口/协作/数据流） | 测试方式 | 对应需求 |
|------|------|------------------------------|----------|----------|
| game-core | 1 | 玩法闭环接口：`Difficulty` 参数表、`GameState` 构造/`set_direction`（含 180° 反向禁止）/`step()`（移动/吃食/碰撞/得分）/`snapshot()`/`status`；反向禁止、食物不与蛇身重叠、撞墙/撞身结束 | pytest 确定性用例（无 GUI） | FR-01~04 |
| game-core | 2 | 暂停状态机扩展（`toggle_pause` 暂停定格/方向输入不生效）、加速曲线（随得分/长度加速）、难度档位参数化 | pytest 参数化用例（三档×曲线） | FR-05/12、NFR-01 |
| platform-storage | 2 | `get_user_data_dir()` 三平台定位、`HighScoreStore` 的 `load/save/reset`、原子写（临时文件+os.replace）异常退出不损坏 | pytest（tmp_path 隔离） | FR-13、NFR-06/07 |
| gui-renderer | 1 | `Renderer.render(snapshot)` 绘制蛇/食物/背景/HUD、`fps_metric()` 帧率统计；渲染只读 core snapshot 不直接改状态 | pytest + SDL dummy 渲染断言 | FR-06/07、NFR-01 |
| gui-renderer | 3 | 平滑插值动画（逐帧插值非整格跳变）、皮肤系统 ≥3 套（经典/深色/色盲友好，色盲不以颜色为唯一区分）、`handle_resize(w,h)` 等比缩放 | pytest + 截图对比断言 | FR-07~10、NFR-04 |
| game-app | 1 | 装配主循环：输入映射（WASD/方向键/P/ESC）→ core → renderer 数据流、开始/结束/重开/退出流程 | 事件注入驱动 + pytest | FR-01/04/11 |
| game-app | 2 | 难度选择界面（开局选档、游戏中不可切换）、暂停/继续、最高分展示与重置（联动 storage） | 事件注入驱动 + pytest | FR-05/12/13 |
| game-app | 3 | 皮肤切换 UI（对局不中断生效）、设置界面 | 事件注入驱动 + pytest | FR-10 |
| game-app | 4 | 可读错误提示（图形环境缺失等，无裸 traceback）、退出 1 秒内无残留进程、性能指标（≥60FPS/输入延迟≤1 节拍/内存≤300MB） | 进程级脚本 + pytest | FR-11、NFR-01~03 |

### 2.2 用例组织方式（MTO 落盘约定）

```
workspace/snake-linux/{模块}/it/iter-{N}/     # 每模块每迭代一个用例目录
├── case.md          # IT 用例文档（MTO 产出，TE 评审 PASS 后才能写代码）
└── test_*.py        # 测试代码（评审通过后实现，运行于 tests/v2.0.0/ 框架下）
```

- 用例编号：`IT-{模块}-{iter}-{序号}`，如 `IT-game-core-1-03`；ST 用例编号 `ST-{序号}`；
- 每个用例文档条目含：关联需求（FR/NFR 编号）、前置条件、步骤、预期、优先级（P0/P1/P2）；
- 迭代 4 的 app 全链路用例需在迭代 1~3 用例基础上做跨迭代回归（见 §3.2）。

### 2.4 IT 通过标准

- 用例文档全部经 TE 评审 PASS（铁律，见 §5）后方可写测试代码；
- 自动化执行：P0/P1 全部 PASS（无 skip），P2 允许 SKIP 但须留记录；任一 P0 失败 = 该模块迭代阻塞。

## 3. ST 方案（版本级，STO 执行）

### 3.1 端到端主链路（用户旅程，P0）

| ST 用例 | 用户旅程段 | 步骤要点 | 关键断言 |
|---------|-----------|----------|----------|
| ST-01 开箱即用 | 下载 → 启动 | 干净机器（无 Python/Node/Java 预装）下载单文件 → 直接启动 | 免安装免配置直接进入开始界面（FR-14） |
| ST-02 开始 → 选难度 | 开局 | 开始界面 → 三档难度选择 → 开始新局 | 选档生效且游戏中不可切换（FR-05/11） |
| ST-03 完整对局 | 游玩 | 方向键吃 ≥3 食物 → 暂停/继续 → 切换皮肤 → 撞墙结束 | 吃食增长、暂停恢复原位、皮肤即时生效、结束画面稳定显示得分与重开/退出入口（FR-01~04/06~10/12） |
| ST-04 最高分持久化 | 重启 | 结束 → 记录得分 → 退出 → 重启 → 查 HUD/开始界面 → 重置 | 重启最高分保留；重置归零；数据仅本地（FR-13、NFR-06） |
| ST-05 退出卫生 | 退出 | 游戏中/暂停中/结束画面三种时机退出 | 1 秒内干净结束、无残留进程（FR-11） |
| ST-06 用户指南走查 | 文档 | 按用户指南五节（下载运行/键位表/难度/皮肤/暂停/平台差异/已知限制）逐步复现 | 文档五节齐全且可复现启动（FR-16） |

### 3.2 回归范围（跨迭代协同）

- 每次迭代收口执行**全量自动化回归**（core/storage/renderer/app 已实现用例全跑），防跨模块回归（core 接口变更影响 renderer/app）；
- 迭代 4 收口执行**验收全量**：验收标准 1~7 全量核对 + 三平台兼容矩阵（ST-07）+ 性能基线（ST-08）；
- 关键回归锚点：core `snapshot()` 接口契约（renderer/app 均依赖）、难度参数表、storage 数据格式——接口变更必须同步更新下游用例（TE 评审把关）。

### 3.3 发布就绪度判定（ST 出口口径）

| 维度 | 口径 | 门槛 |
|------|------|------|
| 功能实现率 | 验收标准 1~7 逐条核对（FR-01~16/NFR-01~07） | 100% 实现且可验证，无「未验证」遗留 |
| 用例通过率 | 全量自动化用例（UT+IT+ST 自动化部分） | P0/P1 100% PASS，P2 无未闭环缺陷 |
| 覆盖率口径 | 需求→用例映射表（§4）逐条勾选 | 每条 FR/NFR 至少 1 个用例，P0 需求全覆盖 |
| 兼容矩阵 | Windows 10/11、macOS 12+（Intel+Apple Silicon）、Ubuntu 22.04+ 各跑通 1~5 轮完整对局（ST-07） | 三平台全部 PASS，无平台性 P0 缺陷 |
| 性能 | 帧率 ≥60FPS、P95 帧时间 ≤25ms、输入延迟 ≤1 节拍、内存 ≤300MB（ST-08） | 不达标记缺陷单，P0 判定不依赖性能用例，但发布前须给出实测数据 |
| 缺陷闭环 | 问题单（issue） | 无 P0/P1 未关闭问题单 |

> 任一 P0 失败 = 版本发布阻塞；P2 失败不阻塞（记录缺陷单，随下一版本或评审裁决）。

## 5. 用例评审流程（铁律）

1. MTO 写 IT 用例文档（`{模块}/it/iter-{N}/case.md`）、STO 写 ST 用例文档（版本级 ST 目录）→ 提交 TE 评审；
2. TE 评审（PASS/FAIL 意见）：覆盖性（需求→用例映射齐全，对照 §4）、可执行性（前置/步骤/预期明确）、与整体测试方案一致性；
3. **PASS 后才允许写测试代码**（铁律）；FAIL 打回修订后重评；
4. 评审意见落盘（`release_module ... case ... PASS|FAIL` 门禁记录）。

## 6. 优先级与缺陷管理

- P0：核心功能/发布阻塞（玩法闭环、难度、暂停、最高分、退出卫生、开箱即用、跨平台）；
- P1：重要功能边界（动画平滑、皮肤切换、缩放、错误提示）；
- P2：体验增强/视觉细节（美观基线、HiDPI 细节）；
- 缺陷统一走 `issue {项目} open/fix/close` 问题单闭环；open>0 卡模块/版本门禁（机制守护，见流水线约定）。
