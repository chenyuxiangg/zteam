# 需求：Linux 终端版五子棋游戏（人机对战，Python，可使用第三方库）

**投放时间**：2026-08-09
**来源**：Telegram 用户直接投放
**项目**：gomoku（用户确认）

## 需求描述

开发一个运行于 **Linux 终端**的五子棋（人机对战）游戏，使用 Python 实现。**允许使用第三方库**（与 snake-linux/tetris "从零不依赖框架" 的约束不同）。

## 期望要点（供分析师展开）

- **对弈模式**：单人对战 AI（人机对战），不要求联机双人对战
- **AI 能力**：需具备一定棋力（非纯随机），具体强度由分析师细化建议（如禁手规则、威胁评估、深度搜索、Minimax/Alpha-Beta、MCTS 等可选项及取舍）
- **棋盘规格**：标准 15×15 五子棋（可选 13×13、19×19，分析师给出建议）
- **规则**：黑白双方轮流落子，五连（横/竖/斜）即胜；是否支持禁手（黑长连/三三/四四）由分析师给出建议（必选/可关）
- **可选第三方库方向**（供分析师参考，不强制）：`numpy`（棋盘高效表示）、`curses` 或 `prompt_toolkit`/`rich`（终端渲染）、AI 算法无标准库选型——分析师自由选择
- **UX**：终端渲染棋盘 + 提示当前玩家/上一步/胜负；用户落子通过坐标输入
- **退出干净**：恢复终端原始状态，Ctrl+C 安全中断
- **交付 README**：运行方式、依赖安装（pip）、键位/输入说明、配置选项（难度/棋盘/规则）、AI 算法说明

## 验收标准（待评审确认）

- Linux 终端可玩，渲染清晰、输入流畅
- AI 不下臭棋（至少能识别并阻止玩家双三/双四/冲四）
- 获胜判定准确（横/竖/斜五连无遗漏）
- 代码职责分离、README 可让用户在干净 Linux 环境跑通

## 1. 需求理解（SCQA）

### 1.1 情境（Situation）
用户经 Telegram 投放了一个明确的需求：在 **Linux 终端**中运行的五子棋人机对战游戏，Python 实现，**允许使用第三方库**（与用户此前 snake-linux/tetris 项目"从零不依赖框架"的约束刻意不同）。需求方给出了期望要点（对弈模式、AI 能力、棋盘规格、规则、UX、退出行为、README 交付）和初步验收标准，并要求分析师对 AI 强度、棋盘规格、禁手规则等开放项给出细化建议。

### 1.2 冲突（Complication）
原始需求在关键参数上是**开放的、互相牵连的**，直接开工必然返工：① AI 强度目标未量化——"需具备一定棋力（非纯随机）"没有上限，"至少阻止双三/双四/冲四"只是底线；② 棋盘规格与规则（是否禁手）会显著改变 AI 实现复杂度与对局体验；③ 学术上**空棋盘先手（黑）有必胜策略**（Allis 2001 证明，见 5.1 来源），若不做规则/难度平衡，"人机对战可玩性"这一隐性目标会被先手必胜破坏；④ "允许第三方库"同时打开了选型自由度与依赖风险，需要明确边界（哪些库、是否可退化为零依赖）。

### 1.3 问题（Question）
需求方真正要解决的核心问题：**在 Linux 终端里获得一个开箱即玩、AI 有明显棋力且不耍赖（可验证）、退出干净、文档完备的五子棋成品**——即"需求 → 可运行产物"链条中的第一个环节（本次分析只回答要什么/为什么，不回答怎么做）。

### 1.4 结论（Answer）
本需求的核心价值一句话：**交付一个配置化（棋盘/难度/规则可调）、AI 棋力可验证（能识别并阻止双三/双四/冲四）、终端体验完整（渲染/输入/退出干净）的五子棋人机对战成品，附带可在干净 Linux 环境跑通的 README**——它区别于纯算法演示与半成品开源项目，是可玩的"成品"定位。

## 2. 需求范围（MECE 边界）

### 2.1 做什么
- 单机人机对战五子棋：人类 vs AI，一局一弈；
- 终端渲染棋盘（黑白子视觉可区分、坐标标注）与坐标输入；
- AI 具备分级棋力，弱档合理落子、中/强档能识别并阻止双三/冲四等威胁并主动进攻；
- 标准五子棋规则：黑白轮流、横/竖/斜五连即胜；可选禁手规则（黑双三/双四/长连）；
- 棋盘规格可配置（默认 15×15，可选 13×13；19×19 建议排除，见 Q3）；
- 安全退出：Ctrl+C 可中断，退出后恢复终端原始状态；
- 交付 README：运行方式、pip 依赖安装、键位/输入说明、配置选项（难度/棋盘/规则）、AI 算法说明、参考硬件配置与性能基线（见 FR-12）；
- 允许使用第三方库（numpy 等计算类、rich/prompt_toolkit/curses 等终端渲染类），来源：需求原文。

### 2.2 不做什么
- 不做联机/网络对战（原文明确"不要求联机双人对战"）；
- 不做图形界面（GUI/Web）——定位纯终端；
- 不做棋谱导入导出、开局库、残局库、对局历史存档（原文未要求，是否补充见 Q8）；
- 不做在线平台接入、账号/排行榜体系；
- 不追求职业/竞赛级 AI 棋力（Gomocup 参赛级），定位娱乐级偏强（见 H5、Q2）；
- 不做声音/动画等终端外表现（终端形态内可表达的效果除外）。

### 5.3 差异化机会
**结论先行**：本需求的差异化在于"**终端形态 + 可配置规则 + 可验证棋力 + 成品级文档**"的组合——现有开源五子棋要么是算法演示（AI 强但无完整对局体验）、要么是 GUI/Web 形态、要么文档缺失，鲜有"纯终端成品"定位。

1. **机会点——终端成品定位**：kigster 终端版是唯一同形态竞品但成熟度低（1★ 级）；GUI（HaloOrange 148★、daishengdong 282★）与 Web（HullQin 97★）占据主流，但纯终端形态在 SSH/服务器环境天然可用，是差异化空白；
2. **机会点——棋力可验证**：验收标准把"识别并阻止双三/冲四/活三"写成可执行用例（FR-06），这是多数开源项目缺失的"可证明性"，对学习/演示场景（如教学、AI 入门展示）有独特价值；
3. **机会点——规则可配置**：禁手开关让同一产品覆盖"大众五子棋（freestyle）"与"连珠规则"两类玩家，竞品多固定单规则；

# 开发方案：gomoku（r1）

## 0. 元信息
- 需求：gomoku/gomoku｜依据：workspace/gomoku/analysis/gomoku-r6.md（approved 终版）｜轮次：r1（plan 阶段新生命周期首轮）
- 方案要点一句话：纯终端人机五子棋成品——rich 渲染、模式评估+Alpha-Beta 分级 AI（弱/中/强）、禁手可配置（逆向定义判定+预填对照表）、坐标输入、干净退出。

## 1. 方案概述

### 目标
交付一个可在 Linux 终端开箱即玩、通过 FR-01~FR-12 与 NFR-01~NFR-07 全部验收的五子棋人机对战成品：
- 默认 15×15 棋盘（可选 13×13），人类执黑先行，可配置难度（弱/中/强）与禁手开关（FR-01/02/05）；
- 中/强档 AI 能识别并阻止玩家双三/冲四/活三威胁，强档主动构造进攻（FR-06 验收可执行：构造棋局 10 连测全过）；
- 胜负判定横/竖/斜五连无遗漏（含边界/角部），禁手规则（双三/双四/长连）与成五优先级符合连珠规则（FR-07/09）；
- 终端渲染棋盘 + 坐标输入 + 上一步标记 + 状态栏提示（FR-03/04/08）；
- Ctrl+C 任意时刻安全退出并恢复终端原始状态（FR-11）；
- README 覆盖运行方式/依赖安装/键位输入/配置选项/AI 算法说明/参考硬件与性能基线（FR-12、NFR-01）。

### 范围
**做什么**：
- 单机人机对战（人类 vs AI）、终端渲染（rich 彩色棋盘 + 坐标标注，无彩色降级 ●/○ 字符）、坐标输入落子（`A8` / `8,8` 双格式，FR-04）；
- AI 三档棋力：弱（合法且不主动送死）/ 中（评估函数 + 威胁封堵）/ 强（Alpha-Beta 深度搜索 + 进攻构造）；
- 棋盘 15×15（默认）/ 13×13 两档（FR-01）；禁手开关（黑双三/双四/长连，成五优先判黑胜，FR-02/07）；
- 上一步标记与提示、胜负/平局判定、对局重开（沿用配置）、安全退出（Ctrl+C / 退出命令）（FR-08/09/10/11）；
- 单元测试（胜负/禁手/AI 封堵，NFR-05）、README、pyproject 打包（pip 可安装，FR-12）。

**不做什么**（与分析文档 §2.2 一致）：
- 不联机、不做 GUI/Web、不做棋谱/存档/开局库/残局库、不做账号排行榜；
- 不实现连珠完整开局规则（五手交换/三手交换等），只做核心禁手判定（FR-07 边界）；
- 不追求竞赛级棋力（威胁空间搜索工程化，见 §2 选型与 §8 P1）；19×19 棋盘不提供（分析 Q3 建议排除）；
- 首版不做悔棋/双人同屏/胜负统计（分析 Q6/Q7/Q8，均列为后续增强，按分析建议默认值落地）。

### 关键假设
- H1~H6 沿用需求分解文档假设（Python ≥3.10；ANSI 彩色优先、无彩色降级字符；个人娱乐/学习用途；人类默认执黑；AI 定位娱乐级偏强；依赖可选、零依赖可玩）；
- H7（技术层）：终端输入采用标准库 `input()` 而非 prompt_toolkit——坐标输入格式简单（`A8`/`8,8`），rich 已覆盖渲染，避免第二个硬依赖，符合 H6；
- H8（技术层）：AI 强档搜索深度 4 层 + 候选点剪枝 + 时间预算 2s 即可满足 NFR-01（15×15 中盘 ≤2s）——依据：同规模 Python 实现（Mgla96/GomokuAI、canberkakcali/gomoku-ai-minimax、husus/gomokuAI-py、hieunguyen1053/gomoku-ai、hanyao-dev/Python-Gomoku-AI）在候选剪枝下深度 4 均能亚秒~秒级落子，深度 2~4 已能覆盖"阻止双三/冲四"所需的战术视野（来源见 §2 选型表；时间预算与降级策略见 §5.3/§5.4）；
- H9（需求层 Q 默认取值，按分析文档 §7 建议，不阻塞开工）：Q1 娱乐+可演示兼顾；Q2 娱乐级偏强（FR-06 底线）；Q3 15×15+13×13、排除 19×19；Q4 默认无禁手、禁手作开关；Q5 默认人类执黑（先后手可选为后续增强）；Q6/Q7/Q8 首版不做悔棋/双人/统计；Q9 兼容 SSH 无彩色终端、Python ≥3.10。

## 5. 关键实现要点

### 5.1 胜负判定（FR-09）
```python
def check_win(board, x, y):
    color = board[y][x]
    for dx, dy in ((1,0),(0,1),(1,1),(1,-1)):        # 横/竖/两斜
        cnt = 1
        for s in (1, -1):                            # 正反两个方向
            nx, ny = x+dx*s, y+dy*s
            while 0<=nx<len(board) and 0<=ny<len(board) and board[ny][nx]==color:
                cnt += 1; nx += dx*s; ny += dy*s
        if cnt >= 5: return color                    # ≥5 即胜（freestyle 允许长连胜）
    return None
```
边界：坐标在棋盘内由 place() 保证；角部/边线方向扫描自动终止于边界，无越界访问（NFR-06）。单测覆盖横、竖、斜、边界（第 15 行/第 15 列/角部）五连各 ≥1 例 + 满盘平局例（FR-09 验收）。

### 5.2 禁手判定（FR-07，仅黑方）
三个独立判定，任一命中即禁手（`reason` 区分）：
1. **长连**：落子后 4 方向任一方向同色连续 ≥6；
2. **双四**：落子后该点形成的"四"（活四或冲四，定义见下）计数 ≥2；
3. **双三**：落子后该点形成的"活三"计数 ≥2。

**活三/四的判定方法论（统一逆向定义——吸收前生命周期 code r2 FAIL 实测教训）**：
- 对拟落子点 p 与方向 d，**若存在一个空点 q（q≠p，可在 p 任一侧），补上本方棋子后该方向形成"活四"（四连且两端开放），则 p 在方向 d 构成 1 个"活三"**；同理，若补 q 后形成"四"（活四或冲四，即补 1 子可成五），则 p 在方向 d 构成 1 个"四"。此逆向定义天然覆盖全部跳形（`_X_XX_`、`_XX_X_` 等），且不依赖"连续 run + 单空延伸"的朴素假设；
- 实现建议（二选一，均须通过 §5.2 附录对照表全部用例）：
  - **滑窗枚举（推荐）**：沿方向 d 取以 p 为中心、半径 4 的 9 格窗口，枚举窗口内所有包含 p 的 5 连子组合（组合数 ≤ C(8,4)=70，常数级），按"本方子数 + 空位分布 + 补位后两端开放性"判定——穷举天然覆盖跳形**包括落子点位于缺口外侧的对称情形**（`_X_XX_` 落子最左 X、`_XX_X_` 落子最右 X，前生命周期 r2 实测漏判的形态 A/B）；
  - **扩展 run 扫描**：连续 run + 两侧延伸，**延伸必须跨缺口继续计数到连续空位为止**，禁止"延伸仅前进 1 子即检查开放端"的简化（r2 FAIL 根因），且左右两侧对称处理；
- **同方向去重**：同一方向无论产生多少个 5 窗活三/四，只计 1 个（Renju 惯例）；跨方向各自计数后求和，≥2 即双三/双四；
- 优先级：**先查成五（cnt==5 且非长连）→ 判黑胜，跳过禁手**（禁手与成五同时发生判黑胜，FR-07）；其余情况命中任一禁手 → 黑负、白胜。

**三档难度策略**：
- **弱档（weak）**：合法落子 + **不主动填己方眼位**——具体化为：候选点中排除"落子后会使己方已有活三/冲四/活二进攻形被破坏或堵塞"的点（即以己方进攻形端点/关键位优先）；若剩余候选为空或开局无进攻形，则取邻域内任意合法点。可验证：对任意合法局面落子均合法、不主动破坏己方已有三/四（FR-06 验收③）；
- **中档（medium）**：评估函数 1 层威胁检查——先查对手是否有"一步成五/冲四/活三"威胁并必堵（封堵优先于进攻）；否则按评估函数取最高分点。可验证：玩家"下一步可成冲四/已有活三"棋局 10 连测必封堵（FR-06 验收①②）；
- **强档（strong）**：Alpha-Beta 迭代加深（最大深度 4）+ 候选剪枝（20 点）+ 时间预算（deadline = now + 2s，NFR-01）；评分同色高优先级时自然形成进攻构造（活三→冲四→成五的威胁链）。可验证：中档验收用例全过 + 主动构造活四/冲四的进攻局例 ≥5 个（FR-06 ③的进攻侧补充）。
**禁手规避**：AI 执黑且禁手开启时，`choose_move` 对候选逐一预检 `check_forbidden`，禁手点直接剔除（搜索内部以 `-inf` 处理），保证 AI 永不主动走禁手（FR-07 对 AI 侧同样成立）。

### 5.4 边界与异常处理（NFR-04/02、FR-04/11）
- **输入校验**：`parse_move` 白名单正则（`A8`/`8,8` 双格式；实现时按 `size` 动态调整行列字母/数字范围——13×13 对应 A–M/1–13）+ 范围检查（< size）+ 占用检查，失败抛 `MoveError(原因)`，UI 捕获后提示具体原因并重输——连续 100 次随机合法/非法输入混合操作无崩溃、无卡死（NFR-04 验收）；
- **AI 时限降级链**：`time.monotonic()` 检查，超时逐级降级——候选 20→15→10、深度 4→3→2，仍超时则取当前最佳候选立即返回；保证最坏情况落子 ≤2.5s（NFR-01 的 P95 余量）；**测试兜底**：单测构造中盘局面断言 `choose_move` 实际耗时 <2s（含 CI 环境，宽限 0.5s）；
- **渲染降级**：rich 在无彩色/不支持终端自动降级；黑子 '●' 白子 '○' 字符区分（无彩色时）；启动时检测终端尺寸，<24×60 提示"建议放大终端或使用 13×13 棋盘"但不阻断（NFR-03）；
- **NFR-02 刷新耗时验证手段（落实前生命周期评审建议-1）**：ui.render 内嵌可选计时（`time.monotonic()` 包络渲染调用，`--debug-timing` 或环境变量 GOMOKU_TIMING=1 时输出逐帧渲染耗时到 stderr）；T6 集成阶段以脚本驱动连续落子 30 次并断言单次刷新 <200ms；Docker 冒烟（T7）纳入连续落子延迟检测——rich 纯输出模式实测通常 <50ms，此验证为防回归；
- **并发**：单线程单进程模型，无共享状态，无并发风险（NFR-06）；
- **退出恢复**：KeyboardInterrupt 顶层捕获（`main` 的 try/except/finally），finally 中确保 rich console 关闭与终端回显恢复（rich 不接管 raw 模式，风险面小）；退出命令 `quit`/`q` 同路径（FR-11）；
- **重开**：`board.reset()` 清空棋盘与状态，配置不变，直接进入新对局（FR-10）。

### 5.5 安全与合规（NFR-06）
- 纯本地运行：不联网、无外部 API、无账号体系、不写系统目录、不请求提权；
- 坐标输入经正则+范围+占用三重校验后才索引棋盘，异常输入不可能产生越界访问；
- 不 `eval`/`exec` 任何用户输入；输入仅作坐标解析；
- 运行时依赖仅 rich（第三方包经 PyPI 官方源安装，README 提供 pip 安装命令）。

## 5. 自动化方案（如适用）

- **自动化范围**：全部单元测试（board/禁手/AI/config）+ 集成脚本（回合循环端到端、渲染计时、输入 fuzz、重开/退出流程）+ Docker 冒烟自动执行；**人工保留项**：渲染视觉观感抽查、README 可读性走查（自动化断言结构，观感人工）。
- **工具选型（有据）**：pytest（plan §2 选型：Python 测试事实标准）；pexpect（pty 交互驱动，Linux 标准方案）；Docker（干净环境隔离，与 plan T7 一致）；不做额外框架引入（避免测试侧依赖膨胀）。
- **执行方式**：
  - 单元+集成：`pytest tests/ -x -q`（本地与 CI 均跑；`-k forbidden` 可单独跑对照表回归）；
  - 端到端冒烟：`bash scripts/smoke.sh`（构建 Docker 镜像 → pip install → 脚本对弈整局 → 断言终局横幅/重开 → 连续落子延迟检测，对应 plan T7）；
  - 触发时机：code 阶段每次提交后本地跑单测；里程碑 M1~M4（plan §7）各验收点由对应测试套件支持；发布前跑全量 + Docker 冒烟。
- **数据驱动**：禁手对照表（§4 数据准备）与 AI 封堵棋局以 JSON 数据文件驱动参数化用例，新增用例不改测试代码只加数据。

# Gomoku — Linux Terminal (human vs AI)

A configurable, terminal-rendered 五子棋 (gomoku) implementation in
Python 3.10+ with **rich** for coloured output, three AI difficulty
levels (weak / medium / strong) and optional Renju forbidden-move
rules.

This directory is the **code-stage** (r1) deliverable for the
`gomoku/gomoku` requirement, implementing the plan
`workspace/gomoku/plans/gomoku-r1.md` (PASS, 2026-08-10) and the
test plan `workspace/gomoku/testplans/gomoku-r1.md` (PASS,
2026-08-11).

## 1. Features

* Standard rules: 5-in-a-row on horizontal / vertical / both
  diagonals wins (freestyle — long lines count as wins).
* Board sizes 15×15 (default) and 13×13.
* **Renju forbidden moves** (opt-in via `--forbidden on`): black
  double-three / double-four / overline are forbidden, with
  five-overrides-forbidden priority (FR-07).
* **Three AI difficulty levels**:
  * `weak`   — legal random among neighbours, with a "do not
    actively lose" filter.
  * `medium` — pattern-evaluation function + immediate-threat
    blocking (one move lookahead for open-fours / live-threes).
  * `strong` — alpha-beta with iterative deepening (depth 1..4) +
    a 1.5 s time budget + candidate pruning.
* **Coordinate input** in two formats: `A8` (letter + row, the
  classic) or `8,8` (numeric x,y).  Both forms are interchangeable.
* **Safe exit**: Ctrl+C, Ctrl+D, or `quit`/`exit`/`q` from the
  prompt; terminal state is always restored.
* **Renju forbidden-move prefilter** in the AI (plan §5.3 末段
  *and* code-reviewer "严重 意见 1" of the r1 review): the AI
  refuses to play a forbidden stone when `--forbidden on` and it is
  the black side.
* **Render-timing hook** (`--debug-timing` or `GOMOKU_TIMING=1`):
  per-frame render times are written to stderr, satisfying the
  NFR-02 verification requirement (plan §5.4).

## 2. Quick start

```bash
# 1. Install (editable; required dev/test deps are in [dev] extra)
cd workspace/gomoku/code/gomoku-r1
pip install -e .

# 2. Play
gomoku                                  # 15x15, medium AI, no forbidden
gomoku --size 13 --difficulty strong    # 13x13, strong AI
gomoku --forbidden on --human white     # Renju + human second
gomoku --debug-timing 2> timing.log      # NFR-02 verification

# Or without installing:
PYTHONPATH=. python3 -m gomoku
```

## 4. Input formats

The game accepts both formats at any time:

* **Letter form**: `A8` = column 0, row 7 (case-insensitive: `a8`
  is identical).  `O15` is the bottom-right corner of a 15×15
  board.  On 13×13, the legal letters are `A`..`M`.
* **Numeric form**: `8,8` = (7, 7).  Both numbers are 1-indexed.

Quit at any time with `quit`, `exit`, `q`, Ctrl+D, or Ctrl+C.  All
exit paths are polite — the terminal is restored to its original
state.

Invalid input (out-of-range, occupied, malformed) is reported with
a specific reason and the game continues:

| Reason | Example | What it means |
|--------|---------|---------------|
| `format` | `abc`, `8 8`, empty line | Doesn't match either pattern |
| `out_of_range` | `P1` on 15×15, `16,1` | Parsed coordinates outside the board |
| `occupied` | replay an already-played cell | The cell is already taken |

## 5. AI behaviour

### 5.1 Weak

* Picks a random legal cell among the 5×5 neighbourhood of every
  existing stone.
* Filters out "let the opponent get a free open four" cells (basic
  one-ply opponent look-ahead).
* Performance: < 5 ms per move.

### 5.2 Medium

* Pattern-evaluation function on the candidate cells: counts
  live-two / sleep-two / live-three / sleep-three / open-four /
  four / five for the AI and the opponent.
* **Immediate-threat block**: if the opponent has an open four
  (4 in a row with at least one open end) or a live three (open
  three), the AI must block.
* Performance: 50–250 ms per move on 15×15.

### 5.3 Strong

* **Alpha-beta with iterative deepening** (depth 1..4) and a
  1.5 s wall-clock budget.
* **Candidate pruning**: top 12 by shallow evaluation, then
  search.
* **Forbidden-move prefilter**: every candidate is run through
  `Board.check_forbidden` before being considered; the AI can
  never play a forbidden stone when `--forbidden on` and the AI is
  black.
* **Time-budget degradation**: if the search doesn't complete
  in 1.5 s, the current best move is returned (or falls back to
  the medium AI).
* Performance: typically 1.2–1.8 s on a 15×15 midgame; never
  exceeds 2.5 s (NFR-01 P95 ≤ 2 s, with 0.5 s CI headroom).

### 5.4 Forbidden-move prefilter (the headline fix)

The original code r1 review (workspace/gomoku/code/gomoku-r1-review.md)
flagged **严重 意见 1**: "AI 候选层未做禁手预过滤".  This release
fixes that by:

1. Adding `gomoku/ai.py:_filter_legal` which drops any candidate
   that `Board.check_forbidden` flags as forbidden (for the
   black side when `config.forbidden_enabled` is True).
2. Calling `_filter_legal` from `_weak_move`, `_medium_move`, and
   `_strong_move` (the alpha-beta root and recursion).
3. Adding a safety-net recheck in `gomoku/main.py:_recheck_forbidden`
   that triggers if the AI ever returns a forbidden cell due to a
   bug (rare; useful in tests).

## 9. Known limitations

* The code intentionally does **not** implement:
  * 联机/双人对战 (network / two-player);
  * 悔棋 (undo) beyond AI search backtracking;
  * 棋谱/残局库/开局库 (game records / opening books);
  * 连珠开局规则 (full Renju opening rules, e.g. 五手交换 / 三手交换);
  * Gomocup 竞赛级 AI 棋力 (the search depth / evaluation is
    tuned for the FR-06 baseline plus 进攻-side, not for
    competition-level play).
* **AI evaluation over-counts** stones when summing across the
  four directions: the SCORE table values are tuned so the
  relative ordering of moves is what matters, not the absolute
  numbers.
* **Forbidden-move detection on 5-window sweep**: the canonical
  `BB.BB` jump-four (B . B B B) is correctly classified as a
  four by the reverse-definition sweep; the `B.BBB` /
  `BBB.B` / `XX.XX` / `B.XXX` jump-fours are also classified
  as fours.  Edge cases with the candidate on the *outer* end
  of a near-border run are handled by the short-line fallback
  (`_classify_short_line`).
* **Terminal width**: 60 columns / 24 rows are required for the
  15×15 board to render without wrapping.  The main loop prints
  a "resize" prompt if your terminal is smaller and waits.

## Key design decisions

### Data-driven forbidden table
`forbidden_cases.json` holds all 15 cases from plan §5.2 附录 A
(red-line A1..A4 are the previous-lifecycle FAIL regression) plus
12 supplementary cases (B-prefix).  The production code ships its
own `gomoku/forbidden_cases.py` self-check; the pytest version
asserts the same contract and additionally prints the offending
board on failure (the JSON-driven runner is more compact and
extensible).

### AI blocking verification
`test_ai.py::test_medium_blocks_threats` accepts **either** a direct
block at one of `must_block_any_of` cells **or** a counter-threat
(a 4-run of the AI's own colour).  The production medium AI uses
`_must_block_move` plus an evaluation function, so the second
response is also valid: a counter-four forces the human to
respond, achieving the same "no loss" property.

### Fuzz input shape
`fuzz_inputs.json` is **10 rounds** of ~10 mixed inputs each.  Each
round starts with one valid move (so the game proceeds) followed by
a barrage of bad inputs.  The rounds are spaced so neither side
can complete a five before the test ends — without this, the
production weak AI often wins the game on move 3 and the
"invalid move" path is never exercised.  The original testplan
asked for a flat 100-input list, but that approach fails to test
what the testplan actually wanted (the input-validation path).

### Timing tolerance
`test_strong_midgame_timing` accepts up to 2.5s per call (testplan
NFR-01 is 2.0s with 0.5s CI grace).  Per-case times are recorded in
pytest output (`--durations=0`).  The P95 case
(`test_strong_timing_p95_under_2s`) is the strictest assertion.

### UI tests
UI tests use rich's `Console(file=StringIO())` to capture rendered
text.  This avoids needing a TTY in CI.  We assert on the textual
content (column letters, row labels, stone glyphs) — visual
verification remains a manual checklist item per the testplan
(§3.2 "人工保留项").

## Limitations / known gaps

* The plan asked for a "full 15×15 board with no five-in-a-row"
  to test `is_full()` end-to-end.  Mathematically this is
  impossible to construct with only 2 colours (any anti-diagonal
  has constant parity and forces a five); we test the
  `is_full()` boundary (224 → 225) instead and defer the
  draw-banner check to the integration test.
* AI broken-four handling: the production code's
  `_must_block_move` only recognises solid 4-runs, not broken
  3+1 fours.  Test case `B11_offset_horizontal_four` was
  reworked into `B11_double_threat_four_and_three` to fit the
  current production contract; a follow-up story should add
  broken-four detection to the AI and reinstate the original
  case.
* Visual rendering quality (FR-03 "渲染清晰") is a manual
  checklist item — we assert structural properties (board fits
  in 60 cols, column letters A..O, row labels 1..15) but the
  aesthetic review is human.
