## 2. 评审意见列表
- **[建议-1]** NFR-02 "每次落子后棋盘刷新完成 ≤200ms"的验证方式在方案中不显式：§5.4 覆盖了 AI 时限降级与渲染降级，但未给出刷新耗时的验证手段（如 T6 集成阶段增加逐帧计时日志或 docker 冒烟中纳入连续落子延迟检测）。rich 纯输出模式下刷新通常 <50ms，风险低，不阻塞 PASS，建议在 T6 验收点增加备注。
  - 依据：方案 §1 提到 NFR-02 验收但 §7 M3 验收点仅列出 FR 条目；分析 NFR-02 要求"每次落子后棋盘刷新完成 ≤200ms"。
- **[建议-2]** 禁手判定对照表（≥15 例）作为 T3 交付物之一，方案详细描述了逆向定义方法论与红线用例（§5.2），但对照表本身未在方案中预填——code-developer 需自行从方法论推导全部用例文字与棋形图。建议评审意见指向明确（方案已达标），后续设计者可先产出 5~10 例样本附在方案附录中供 code 阶段对照。
  - 依据：方案 §7 T3 要求"禁手判定对照表（≥15 例）"，§5.2 给出了方法论但未附样例棋形。
- **[建议-3]** NFR-01 的参考硬件基线已在 §7 T7/M4 与 §5.3 提及，但方案正文未显式给出硬件基线完整声明（如"x86-64 i5-12400 / ≥8GB RAM"），该信息在分析 NFR-01 中有完整表述，建议方案 §1 或 §7 引用/复述，避免 README 产出时遗漏。
  - 依据：分析 NFR-01 含完整基线声明；方案 §7 T7 要求 README 含"参考硬件与性能基线"，但 §1 仅提"参考硬件与性能基线（FR-12、NFR-01）"未展开。
