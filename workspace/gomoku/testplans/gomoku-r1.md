# 测试方案：gomoku（r1）

## 0. 元信息
- 需求：gomoku/gomoku｜依据方案：workspace/gomoku/plans/gomoku-r1.md｜轮次：r1（requeue 后本运行轮次首轮）
- 测试要点一句话：分层验证——单元覆盖胜负/禁手/undo/AI 封堵与时限降级，系统级覆盖渲染/输入/退出/配置，FR 与 NFR 全量可追溯。

## 1. 测试目标与范围

### 目标
验证交付物通过需求分析文档 FR-01~FR-12 与 NFR-01~NFR-07 全部验收标准，重点：
1. 核心规则正确性：胜负判定（4 方向/边界/满盘）与禁手判定（双三/双四/长连/成五优先/跳活三）无漏判误判（FR-07/09）；
2. AI 棋力可验证：中/强档必封堵玩家双三/冲四/活三威胁（10 例/类），强档主动进攻，弱档合法不送死，禁手开启时 AI 黑方规避禁手（FR-06）；
3. AI 搜索正确性：搜索回溯（place/undo）不污染棋盘，超时降级链（候选 20→15、深度 4→3）行为符合方案（FR-06、NFR-01）；
4. 终端体验完整：渲染无残留错位、上一步高亮、输入容错不崩溃、回合正确切换、重开、任意时刻 Ctrl+C 干净退出（FR-03/04/05/08/10/11）；
5. 非功能达标：强档中盘落子 ≤2s（P95）、启动 ≤2s、无彩色/小终端降级可用、100 次混合输入无崩溃（NFR-01~04）；
6. 交付可验证：Docker python:3.10-slim 干净环境按 README 跑通整局、配置项 CLI 生效且文档可见、禁手判定对照表与 Wikipedia Renju 逐条一致（FR-12、NFR-07）。

### 范围内（做什么测试）
- 单元测试：board.py（坐标解析/落子/胜负/满盘/禁手/undo/棋盘快照）、ai.py（评估/候选/封堵/禁手规避/时限/降级链）；
- 集成测试：Board×AI 对弈模拟、UI 输入循环×Board 交互、AI 搜索 undo 不污染棋盘；
- 系统/E2E 测试：CLI 启动、真实终端对局、非法输入容错、重开、Ctrl+C 退出、终端状态恢复；
- 性能测试：AI 落子耗时（P95）、启动耗时、渲染刷新微基准、超时降级行为；
- 兼容性测试：无彩色终端（字符降级）、最小终端尺寸、终端过小提示、Python 3.10/3.11/3.12；
- 安全与健壮性：随机混合输入 fuzz、极端输入不越界、无网络/无系统目录写入核查；
- 文档与静态检查：README 5 项内容、禁手判定对照表、模块划分、中档评估全盘扫描。

### 范围外（不做什么测试，MECE）
- 不测 GUI/Web/联机（需求明确不做）；
- 不测棋谱/存档/胜负统计/悔棋/双人同屏（Q6/Q7/Q8 明确首版不做）；
- 不测连珠完整开局规则（五手交换等，plan §1 明确不做）；
- 不测竞赛级 AI 棋力（定位娱乐级偏强，Q2）；
- 不测并发/多线程：plan §5.4 明确单线程无共享状态，并发测试无意义（理由：无并发执行路径）；
- 不测跨平台（Windows/macOS）：需求限定 Linux 终端。

## 2. 测试策略（分层）

| 层级 | 策略与侧重 | 通过标准（PASS 定义） |
|------|-----------|----------------------|
| 单元测试（pytest） | board/ai 纯逻辑直测：胜负 4 方向/边界/满盘、禁手 4 类+跳活三、坐标解析、undo API、AI 封堵/禁手规避/时限/降级。fixtures 用固定棋局（Board API 摆子），AI 测试固定随机种子保证确定性 | pytest 全绿；每个 FR-06/07/09 验收型用例独立成 test 函数；无断言被跳过 |
| 集成测试（pytest） | Board×AI 对弈 N 步模拟（回合正确/无连续同方/终局正确）；AI 搜索后棋盘状态复原（undo 正确性）；UI 输入循环注入非法/合法输入流 | 模拟对局断言逐步通过；搜索前后棋盘快照一致；输入流处理后状态正确 |
| 系统/E2E（pexpect 脚本化） | 真实 pty 终端驱动 `python -m gomoku`：固定终端尺寸、注入输入、断言输出；覆盖渲染/输入/重开/退出/终端恢复 | 每个 ST 用例的断言全部满足；退出后 pty 无 ANSI 残留、shell 提示符可正常交互 |
| 性能（脚本采样） | 构造中盘局面（双方各 ≥20 子），强档 AI 采样 ≥20 次取 P95；启动计时用 pexpect 从 spawn 到棋盘出现；降级链用时间预算注入验证 | P95 ≤2s（NFR-01）；启动 ≤2s（NFR-02）；渲染单次 ≤200ms（微基准）；超时返回合法点且降级可观察 |
| 兼容性（E2E 变体） | TERM=dumb 或 NO_COLOR=1 下字符模式可玩；60×24 与 <24×60 两种尺寸 | 无彩色下黑白子以字符可区分且可完整对局；小终端给出明确提示且不渲染错乱 |
| 安全与健壮性（脚本 fuzz） | 随机合法/非法输入混合 100 次循环驱动；极端输入（超长/unicode/空串/边界坐标）直测 parse_move | 全程无崩溃无卡死；所有非法输入均被捕获并提示；无越界访问（进程退出码 0 且无 traceback） |

## 4. 测试环境与数据

### 环境
- OS：Linux（Ubuntu 22.04+ 或同类发行版，与交付目标一致）；Python 3.10/3.11/3.12（至少 3.10 实测，ST-21 覆盖三版本）；

- 工具：pytest、pexpect、strace（ST-23 可选）、time（性能采样）、Docker（ST-19 干净环境冒烟，plan §7 T7）。

### 数据准备
- 固定棋局 fixtures：JSON 文件或 Python 构造器，用 `Board.place` 序列摆出——封堵棋局 10 组（冲四/活三各 5 组以上，基准局面 A/B 见 UTA-03/04）、禁手棋局（双三/双四/长连/成五优先/跳活三各 ≥1）、边界五连 4 组、满盘无五连棋局（脚本生成）；

- fuzz 输入池：合法坐标、越界、占用、乱码、超长、unicode、空串、控制字符按固定比例随机组合（ST-22 用固定种子保证可复现）。

### 环境限制与假设
- 假设 rich 在目标终端可安装（国内网络需镜像源安装，见流水线运维约定）；Docker 镜像拉取同样需可用网络/镜像源；

- AI 测试固定随机种子；若实现引入不确定性，允许放宽为"落点 ∈ 封堵点集合"断言（在测试实现时与 test-developer 对齐）；

## 5. 自动化方案

### 自动化范围与工具选型（有据）
| 范围 | 工具 | 依据 |
|------|------|------|
| 单元/集成测试 | pytest | plan §2 选型（Python 测试事实标准）；覆盖 FR-06/07/09 验收用例；test_board/test_ai 为交付物的一部分（NFR-05） |
| 系统/E2E 交互测试 | pexpect | 需要驱动真实进程的 pty 交互（输入/输出断言/Ctrl+C 信号），pexpect 是标准库生态下终端自动化事实工具，零额外服务依赖 |
| 性能采样 | pytest-benchmark 或自写计时脚本 | 指标简单（P95 ≤2s），自写 `time.monotonic()` 采样脚本即可，避免多余依赖；采样 ≥20 次 |
| fuzz | 自写脚本（固定种子） | 输入域有限（坐标格式），脚本化随机注入即可，无需 property-based 框架（hypothesis 留作可选增强） |
| 兼容性矩阵 | CI 矩阵或本地多版本 | 三版本 Python 跑 ST-19 冒烟，脚本化切换解释器；Docker 容器版本矩阵可选 |
| 干净环境冒烟 | Docker `python:3.10-slim` | plan §7 T7/M4 明确要求：本机环境可能已有依赖残留，Docker 才能证明"干净环境可跑通"（FR-12） |

### 执行方式
- 单元/集成：`python -m pytest tests/ -v`（工作区或包根目录）；关键验收用例单跑：`pytest tests/test_board.py -k "win or forbidden"`、`pytest tests/test_ai.py -k "block"`；
- 系统/E2E：`python -m pytest tests/e2e/ -v`（pexpect 用例，标记 `@pytest.mark.e2e`，与快速单测分离）；
- 性能：`python scripts/bench_ai.py --depth strong --samples 20`（输出 P95）；启动耗时 `python scripts/bench_startup.py`；降级链 `python scripts/bench_ai.py --depth strong --budget 0.05`（极小预算验证 UTA-11）；
- 干净环境冒烟：`docker run --rm -v $(pwd):/app -w /app python:3.10-slim bash -c "pip install . && python -m gomoku"`（交互冒烟按 ST-19 步骤脚本化）；
- 触发时机：开发阶段每模块完成后跑对应单测（对应 plan 里程碑 M1~M3）；成品阶段全量 `pytest`（M4 验收前）；回归在每次修改后全量跑；
- 门禁对接：quality 门禁阶段以"全量 pytest 通过 + 性能指标达标 + E2E 全绿"为自动化闸门输入（具体接入以门禁角色文件为准）。

## 6. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| AI 封堵用例因评估函数随机 tie-break 不稳定（FR-06 验收） | 验收用例 flaky，误报 FAIL | 固定随机种子；断言放宽为"落点 ∈ 封堵点/更威胁点集合"；10 组棋局由 test-developer 与 AI 实现同步构造并人工复核（基准局面 A/B 见 UTA-03/04，作为一致基准） |
