## 2. 评审意见列表

- **[建议]** §5.1 目标格伪代码中 Pinky 的 `offset4(pr, pc, d)` 与 Inky 的 `offset2(pr, pc, d)` 没有展开其计算逻辑（注释仅说「含原版向上 bug」）。建议在伪代码中明确写出 `offset4`/`offset2` 的坐标变换公式（如 `d==UP 时 target = (pr-4, pc-4)`），使 code-developer 无需跳转到 Dossier 原文才能实现。
  - 依据：方案 §5.1 自述「code-developer 须按 TDD 先写单元测试再实现」，若伪代码有未展开的辅助函数，单测编写者需要额外查外部资料方能理解预期行为。

- **[建议]** §4.3 地图设计稿注明「内置地图实测 216/216 全可达」和「鬼屋 row10 col8~13 连通」，但未附验证脚本或输出。建议在 T1 描述中补充：validate_map() 实现后输出一份验证报告（连通性/鬼屋通道/多规格适用性三项）随方案一并提交，作为 FR-03 判定③「多规格适用」的先行证据。
  - 依据：FR-03 验收要求「不同规格地图下上述判定均成立」，内置地图的验证结果可作为方案可行性佐证。

- **[建议]** §8 待确认问题 Q7（最高分持久化）的方案处置为「默认不做」「如需可后续追加（JSON 单文件，影响极小）」。建议在 §3.2 的 game.py 职责中预留一个注释/占位（如 `# 如需最高分持久化：在此处 hook save/load`），降低后续追加时的重构风险。
  - 依据：方案自称「可扩展」且已为 28×31 地图预留扩展说明（§8 Q1），对 Q7 保持同样级别的可扩展性表述更具一致性。

## 3. 遗留事项（仅 PASS 时）

- Q1~Q12 全部在 §8 落定默认值，但截至本轮仍未获需求方答复。若需求方后续答复导致方案变更（如确认 28×31 原版比例需更大终端），只需更新 `--map` 默认值 + README，代码无需改动——方案已为此预留扩展路径（§8 Q1/新增 N2/N3）。
- §5.1 原版向上偏移 bug（Pinky/Inky）复刻与否：方案默认忠实复刻，若需求方不认可可「一行改为修正版」（§8 N1），code-developer 实现时建议将此选择封装为常量 `EMULATE_ORIGINAL_BUG = True` 便于回退。
- §5.4 难度参数采用简化公式（非 Dossier 全表），核心体验（玩家略快/四阶段交替/难度递增）已保持原版原则；若后续需要严格复刻原版数值（Dossier Table A.1/A.2），需替换 §5.4 公式为查表实现，影响 T3/T4 工作量约 +1h。
